ORM benchmarks published by an ORM's author deserve suspicion, and I'd rather earn trust by showing the work than ask for it. So this post isn't mainly about which library won. It's about the four things that made my first numbers wrong while I benchmarked [ant](https://github.com/skudra-go/ant) against GORM 1.31, Bun 1.3, ent 0.14 and plain `database/sql` on PostgreSQL. Two of them made other libraries look slow for reasons that had nothing to do with their code.

The final numbers are at the end, including the rows where ant comes last. Everything is in [`tools/compare`](https://github.com/skudra-go/ant/tree/main/tools/compare), so you can rerun it and tell me where I'm still wrong.

## The setup

Seven benchmarks over a table of 1000 users with 5 posts each:

| Benchmark | Work |
| --- | --- |
| `Read1000` | Every user, 1000 rows |
| `FindOne` | One user by key |
| `FilteredQuery` | `age > 30 AND name LIKE 'user 1%'`, by name, 10 rows |
| `Include100` | 100 users and their 500 posts, in two queries |
| `Insert` | One user |
| `UpdateOneColumn` | `UPDATE ... SET age` by key, without loading the row |
| `LoadEditSave` | Load a user, change the age, save it |

All libraries share one connection pool. Plain `database/sql` is the baseline and stands in for sqlc, which generates the same kind of code. Before any timing, `TestSameQuery` runs one realistic query (users over 18 with their posts, sorted, 10 at a time) through all four libraries and checks that they return the same rows. A benchmark comparing four queries that do different work would be meaningless, and that test is how I know they don't.

## Trap 1: the disk was the benchmark

The first write numbers were noise. Inserts and updates took milliseconds, not microseconds, and the order of the libraries changed from run to run.

The cause was `fsync`. PostgreSQL waits for the write-ahead log to reach disk before it reports a commit, and on my machine (PostgreSQL in Docker on WSL2) that wait was up to 9 ms and varied by about ±90%. Every library's insert is a few hundred microseconds of actual work. The disk wait was ten times larger and random, so it hid the libraries completely.

The fix is one setting in the DSN:

```go
dsn += "&search_path=ant_compare&synchronous_commit=off"
```

With `synchronous_commit=off`, a commit doesn't wait for the disk. You wouldn't run production like this, and that's fine: the disk wait is the same for every library, so removing it leaves only the part that differs. The published results say so next to the table.

## Trap 2: Bun's inserts were slow, and it wasn't Bun

With the disk out of the way, Bun's insert took 1,164 µs. Everyone else was between 400 and 450.

Bun builds SQL with the values inlined into the text, instead of sending `$1` placeholders and arguments separately. pgx, the driver underneath, caches prepared statements by default. Every insert with different values is different SQL text, so pgx prepares it as a new statement each time: an extra round trip per insert, and a cache that never hits.

Setting [`default_query_exec_mode=simple_protocol`](https://pkg.go.dev/github.com/jackc/pgx/v5#QueryExecMode) in the DSN brought Bun's insert to 452 µs, level with the others. The published table keeps the default, because that's what a Bun user gets out of the box, and the README states the 452 µs figure next to it. A comparison that silently tuned one library would be less honest, and one that didn't mention the setting would be unfair to Bun.

A related Bun detail: without `nullzero,notnull,default:current_timestamp` on the timestamp fields, plus database defaults, Bun writes zero timestamps on insert. The benchmark models have those tags, so all four libraries write the same row.

## Trap 3: ent's update sends four statements

ent's `LoadEditSave` took 1,784 µs against roughly 800 for the rest. That looked like a performance problem until I logged the SQL.

ent's `UpdateOne` runs in a transaction and reads the row back after updating it, so one load-edit-save sends four statements where the others send two. That's a design choice, not slowness: you get the saved row back, fresh from the database. But it doubles the round trips, and on a benchmark dominated by round trips it doubles the time. The table keeps the number and the README explains it, because "ent is twice as slow at updates" would be the wrong conclusion to draw.

## Trap 4: the machine was busy

The last one is boring, and I still had to throw away a run because of it. A run taken while something else compiled, or while Docker pulled an image, was skewed, and not evenly: whichever library's benchmarks overlapped the busy minute looked worse.

The published numbers come from a prebuilt test binary with nothing else using the CPU, 10 runs per benchmark, reported as the median:

```sh
go test -run '^$' -bench . -benchmem -count 10 | tee new.txt
go run golang.org/x/perf/cmd/benchstat@latest new.txt
```

Run-to-run spread ended up within ±10%, except plain SQL on `UpdateOneColumn` (±21%) and `LoadEditSave` (±16%).

## The results

## What I take from them

**Small queries cost about the same everywhere.** `FindOne`, `FilteredQuery`, `Insert` and the updates are 2% to 23% over plain SQL in every library. The round trip is most of the number. If you're choosing between these libraries for a typical CRUD service, speed is a weak reason to pick one.

**Change tracking is ant's biggest cost.** With tracking on, ant is the slowest library after GORM on `Read1000` and ties GORM for last on `Include100`. Keeping a copy of every loaded row takes 1.7 times the time and 3 times the memory of `NoTracking` on 1000 rows. With tracking off, ant is the fastest of the four on `Read1000`, 8% over plain SQL, and level with Bun and ent on `Include100`. The lesson for users is to turn tracking off for large reads you won't save. The lesson for me is that the snapshot is worth optimising.

**ant allocates too much.** Bun allocates the least in most rows, close to plain SQL. ant makes 118 allocations to find one row, against Bun's 41. Only ent allocates more, on some rows. None of this shows up in the time on a network round trip, but it shows up in GC pressure under load, and it's the next thing I want to work on.

**The outliers are configuration and design, not speed.** Bun's insert is a driver setting. ent's update is a deliberate re-read. Both are worth knowing about if you use those libraries, and neither says much about their code.

## Rerun it

```sh
make db-up DATABASES=postgres   # from the ant repo root
cd tools/compare
go test -run '^$' -bench . -benchmem -count 10 | tee new.txt
go run golang.org/x/perf/cmd/benchstat@latest new.txt
```

`ANT_PG_DSN` points it at another database. If you find a setting that's unfair to any of the libraries, or a benchmark that measures the wrong thing, [open an issue](https://github.com/skudra-go/ant/issues). I'd especially like results from Linux on bare metal, where `fsync` behaves very differently from Docker on WSL2, and from anyone who knows a GORM or ent configuration I should have used.
