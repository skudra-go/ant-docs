Five ideas cover most of the API. Read this page first, then the rest of the docs will make sense.

## Models are plain structs

A struct maps to a table, its fields map to columns, and the field names decide the column names. There is no base type to embed, no generated code, and no schema file.

```go
// spot-start
type Book struct {
	ID    int64
	Title string
	Pages int
}
// spot-end

type LibraryDB struct {
	ant.Context
	Books ant.Table[Book]
}
```

`Book` is the table `books`, with `id` as its generated primary key. See [defining models](/models/defining-models) for names and overrides.

## A probe names a column

`ant.Fields[T]()` returns a `*T` that never holds data. `&B.Pages` is then a pointer ant can recognise as the `pages` column, and the compiler sees a `*int`, so whatever you compare it with has to be an `int`.

```go
var B = ant.Fields[Book]()

books, err := db.Books.
	// spot-next-line
	Where(ant.Gt(&B.Pages, 100)).
	All(ctx)
// SELECT ... FROM "books" WHERE "books"."pages" > $1
```

See [field probes](/models/field-probes).

## The context is your database

Declare a struct with an `ant.Table[T]` for each model. `ant.Open` fills it in. Tables, transactions and sessions hand you back the same struct type, so `db.Users` works the same everywhere.

```go
type AppDB struct {
	ant.Context
	Users ant.Table[User]
	Posts ant.Table[Post]
}

// spot-next-line
db, err := ant.Open[AppDB](ctx, postgres.Dialect, dsn)
```

`Open` reads every model, so a model that can't be mapped fails here, at startup.

## Errors arrive at the last call

Builder methods such as `Where` and `OrderBy` never return an error. ant collects mistakes along the way, and the call that runs the query returns them. That call always takes a `context.Context` first.

```go
query := db.Users.
	Where(ant.Gt(&U.Age, 18)).
	OrderBy(&U.Name)

// spot-next-line
users, err := query.All(ctx) // runs here, and fails here
// SELECT ... FROM "users" WHERE "users"."age" > $1 ORDER BY "users"."name"
```

These calls run something: `All`, `First`, `Single`, `Find`, `Count`, `Exists`, `Each`, `Insert`, `Update`, `Delete`, `Exec` and `SaveChanges`. Everything before them describes the query.

## Nothing happens behind your back

Reading a field never runs a query. A relation you didn't load stays `nil`. A relation you loaded that has no rows is an empty slice, so you can tell the two apart. Loading is always requested, and always batched: one extra query per relation, however many parents.

```go
user, err := db.Users.Find(ctx, id)

// spot-next-line
fmt.Println(user.Posts == nil) // true: not loaded, and no query ran

// spot-start
user, err = db.Users.Include(&U.Posts).Find(ctx, id)
// SELECT ... FROM "users" WHERE "users"."id" = $1 LIMIT $2
// SELECT ... FROM "posts" WHERE "posts"."user_id" IN ($1)

fmt.Println(user.Posts == nil) // false: loaded, even if there are none
// spot-end
```

Writing is explicit too. Changes to tracked entities are saved only when you call `SaveChanges`.

## What the compiler cannot catch

Generics catch most mistakes. These compile, and ant returns an error when the query runs. [antvet](/tooling/antvet) finds them before that.

| Mistake | Example | Error |
| --- | --- | --- |
| A probe from the wrong model | `db.Posts.Where(ant.Gt(&U.Age, 18))` | `ant.ErrWrongModel` |
| A pointer that isn't a probe | `ant.Gt(&age, 18)` | `ant.ErrNotProbe` |
| A key of the wrong type | `db.Users.Find(ctx, "1")` | `ant.ErrKeyType` |
