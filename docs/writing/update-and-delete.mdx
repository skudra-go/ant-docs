title: Update and delete
description: Bulk update and delete with explicit assignments, the guard that stops accidents, and writes on derived sources.
---

`Update` and `Delete` write straight to the database without loading anything, and return how many rows they touched. To save changes to entities you've loaded, use [`SaveChanges`](/tracking/save-changes).

## Update

Every assignment is explicit, so zero values and `nil` are written like any other.

```go
n, err := db.Users.
	Where(ant.Eq(&U.ID, id)).
	// spot-next-line
	Update(ctx, ant.Set(&U.Age, 0), ant.Set(&U.Bio, nil))
// UPDATE "users" SET "age" = $1, "bio" = $2, "updated_at" = $3 WHERE "users"."id" = $4
```

`UpdatedAt` moves by itself, and an explicit `ant.Set(&U.UpdatedAt, t)` wins. On a model with a [version](/lifecycle/optimistic-concurrency), the version moves on by one:

```go
// UPDATE "docs" SET "views" = ("docs"."views" + $1), "updated_at" = $2, "version" = ("version" + $3)
// WHERE "docs"."title" = $4
```

You can't assign the version yourself. `Update` returns an error before running if you try.

A column takes one value per write. Assigning the same field twice returns an error naming it, because databases disagree on what that means: PostgreSQL and SQL Server refuse it and MySQL keeps the last.

## Change a value relative to the row

`Inc` and `Dec` run in the database, so two writers can't lose each other's update. Use them for counters:

```go
// spot-next-line
_, err := db.Users.Where(ant.Eq(&U.ID, id)).Update(ctx, ant.Inc(&U.Age, 1))
// UPDATE "users" SET "age" = ("users"."age" + $1), "updated_at" = $2 WHERE "users"."id" = $3
```

`SetExpr` assigns any [expression](/queries/expressions), such as a function of another column:

```go
// spot-next-line
_, err := db.Users.Where(ant.Eq(&U.ID, id)).Update(ctx, ant.SetExpr(&U.Email, ant.Lower(&U.Name)))
// UPDATE "users" SET "email" = LOWER("users"."name"), "updated_at" = $1 WHERE "users"."id" = $2
```

Or a subquery:

```go
// spot-start
oldest := ant.SubExpr(db.Users.Where(), ant.Max(&U.Age)).Expr()

_, err := db.Users.Where(ant.Eq(&U.ID, id)).Update(ctx, ant.SetExpr(&U.Age, oldest))
// spot-end
// UPDATE "users" SET "age" = (SELECT MAX("users"."age") FROM "users"), "updated_at" = $1
// WHERE "users"."id" = $2
```

On MySQL, a write whose subquery reads its own table is wrapped in a derived table for you, because MySQL refuses the plain form. See [databases](/reference/databases).

## Delete

```go
// spot-next-line
n, err := db.Users.Where(ant.Lt(&U.Age, 18)).Delete(ctx)
// DELETE FROM "users" WHERE "users"."age" < $1
```

On a model with [soft deletes](/lifecycle/soft-deletes), this marks the rows instead of removing them.

### Delete by relation

Conditions can use relations, which is how to delete with a join:

```go
// spot-next-line
n, err := db.Users.Where(ant.HasNone(&U.Posts)).Delete(ctx)
// DELETE FROM "users" WHERE NOT EXISTS (
//   SELECT 1 FROM "posts" AS "ant_related" WHERE "ant_related"."user_id" = "users"."id")
```

### Delete by key

`DeleteByID` removes one row and returns `ant.ErrNotFound` if there is none.

```go
// spot-next-line
err := db.Users.DeleteByID(ctx, id)
// DELETE FROM "users" WHERE "users"."id" = $1
```

## The no-condition guard

A bulk write with no condition returns `ant.ErrNoCondition`, because a forgotten filter would change the whole table. `Unfiltered` says you mean it.

```go
// spot-start
_, err := db.Users.Query().Delete(ctx) // ant.ErrNoCondition

n, err := db.Users.Unfiltered().Delete(ctx) // every row, on purpose
// DELETE FROM "users"
// spot-end
```

The guard also sees through conditions that can't exclude a row. Those are the dangerous ones, because the code looks filtered.

```go
var none []string

// spot-start
_, err := db.Users.Where(ant.And()).Delete(ctx)                  // refused
_, err = db.Users.Where(ant.NotIn(&U.Name, none...)).Delete(ctx) // refused
// spot-end

n, err := db.Users.Where(ant.In(&U.Name, none...)).Delete(ctx) // fine: deletes nothing
```

A `When` that was skipped leaves the guard on too.

## Limit a write

`Limit` and `Offset` bound a bulk write. Add an ordering to choose which rows. SQL has no `LIMIT` on `UPDATE` or `DELETE`, so ant selects the rows by key in a subquery:

```go
// spot-next-line
n, err := db.Users.Where(ant.Lt(&U.Age, 18)).OrderBy(&U.CreatedAt).Limit(100).Delete(ctx)
// DELETE FROM "users" WHERE "users"."id" IN (
//   SELECT "users"."id" FROM "users" WHERE "users"."age" < $1
//   ORDER BY "users"."created_at" LIMIT $2)
```

This is how you purge in chunks: repeat until `n` is zero, so no single statement locks millions of rows. `Offset` also works without `Limit`, on MySQL and MariaDB too.

## Write through a derived source

`UPDATE` and `DELETE` name only a table. When the query reads from `From`, `FromCTE`, a set operation (`Union`, `Except` and the rest), or `Recursive`, ant selects the matching rows by key in a subquery, so the source's conditions apply. Without that, they would run against every row of the table.

```go
// spot-start
old := db.Users.Where(ant.Gt(&U.Age, 60))

n, err := db.Users.Query().From(old).Update(ctx, ant.Inc(&U.Age, 1))
// spot-end
// UPDATE "users" SET "age" = ("users"."age" + $1), "updated_at" = $2
// WHERE "users"."id" IN (SELECT "users"."id" FROM (
//   SELECT ... FROM "users" WHERE "users"."age" > $3) AS "users")
```

`FromCTE` puts the source in a `WITH`:

```go
// spot-start
old := db.Users.Where(ant.Gt(&U.Age, 60))

n, err := db.Users.Query().FromCTE("old", old).Delete(ctx)
// spot-end
// DELETE FROM "users" WHERE "users"."id" IN (
//   WITH "old" AS (SELECT ... FROM "users" WHERE "users"."age" > $1)
//   SELECT "users"."id" FROM "old" AS "users")
```

The rules, each checked before anything runs:

- The source must select the model's stored key. A source narrowed with `Column` or `Omit` returns an error, as does `Values` of a model whose key is `writeonly`, and `FromRaw`, whose columns ant can't see.
- The sides of a set operation match columns by position, so they must hold the key in the same place. Otherwise SQLite, MySQL and MariaDB would read the missing key as the table being written, and change every row.
- The [no-condition guard](#the-no-condition-guard) counts a derived source as filtered when its rows are. `From`, `FromCTE` and `Recursive` take their source's filter. A union needs both sides filtered, an intersection needs either, and `Except` needs its first side, since a second side that matches nothing leaves every row. A source with no condition is refused, and replacing the source replaces what it counts for.
- SQL Server allows `WITH` only at the start of a statement, so a write after `FromCTE` or `Recursive` returns `ant.ErrUnsupported` there. `From` and set operations work.

## Get the rows back

`UpdateReturning` and `DeleteReturning` return what they touched, in the same statement. Support varies: see [databases](/reference/databases).

```go
// spot-start
changed, err := db.Users.Where(ant.Gt(&U.Age, 18)).UpdateReturning(ctx, ant.Inc(&U.Age, 1))
// UPDATE "users" SET ... WHERE "users"."age" > $2 RETURNING "id", "created_at", ...

removed, err := db.Users.Where(ant.Eq(&U.Name, "Bob")).DeleteReturning(ctx)
// DELETE FROM "users" WHERE "users"."name" = $1 RETURNING "id", "created_at", ...
// spot-end
```

Both apply the same no-condition guard.

## Reloading an entity

`Reload` replaces an entity's columns with what is stored now and discards unsaved changes. Relations are left alone. Use it after a bulk write changed rows you hold.

```go
_, err := db.Users.Where(ant.Eq(&U.ID, user.ID)).Update(ctx, ant.Set(&U.Age, 41))

// spot-next-line
err = db.Users.Reload(ctx, user)
// SELECT ... FROM "users" WHERE "users"."id" = $1
```

:::note[Bulk writes skip the model layer]

`Update` and `Delete` run no hooks and no `SaveInterceptor`, because they load no entities, and a bulk update doesn't touch tracked structs. They do apply [global filters](/lifecycle/global-filters), timestamps and the version.

:::
