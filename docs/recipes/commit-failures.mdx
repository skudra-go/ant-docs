---
title: When a commit fails
description: The one failure where you can't know what happened, and how to make the work safe to repeat.
---

Most failures are simple: the transaction rolled back and nothing happened. One isn't. If the connection drops while a `COMMIT` is on its way, your code can't know whether the database received it. The transaction may have committed even though your code sees an error.

Retrying isn't safe then, because the work may already be done. `ant.Attempts` and `ant.WithRetry` don't retry this case. They retry only failures that are known to have rolled back, which `ant.IsRetryable` decides: deadlocks and serialization failures (see [databases](/reference/databases#retry-deadlocks-and-conflicts) for what each database reports).

When `Tx` returns a commit error, its [observers](/lifecycle/hooks-and-observers#observers) don't run. If the context ended before the commit, ant rolls back instead and returns the context's error together with the rollback's.

```go
type Entry struct {
	ID  int64
	Key string `ant:"unique"`
```

## Make the work safe to repeat

Give each operation a key the client chooses, and store it in the same transaction, behind a unique constraint. A retry then finds the key and returns the first result instead of doing the work again.

```go
type Entry struct {
	ID  int64
	Key string `ant:"unique"`
}

var E = ant.Fields[Entry]()

func transfer(ctx context.Context, tx *AppDB, key string) (*Entry, error) {
	// spot-start
	existing, err := tx.Entries.Where(ant.Eq(&E.Key, key)).First(ctx)
	// SELECT ... FROM "entries" WHERE "entries"."key" = $1 LIMIT $2
	if err == nil {
		return existing, nil // it committed after all
	}
	// spot-end

	entry := &Entry{Key: key}

	// INSERT INTO "entries" ("key") VALUES ($1) RETURNING "id"
	return entry, tx.Entries.Insert(ctx, entry)
}
```

`First` returns `ant.ErrNotFound` when the key is new. Any other error from it is a real failure, so a careful version checks `errors.Is(err, ant.ErrNotFound)` before it inserts.

Two retries that run at the same time can both miss the key. The unique constraint stops the second insert, and `ant.IsUniqueViolation(err)` tells you to read the first one's result.

The [ledger example](https://github.com/skudra-go/ant-examples/tree/main/examples/ledger) does this for transfers, and the [audit example](https://github.com/skudra-go/ant-examples/tree/main/examples/audit) does it with event IDs.

## Check afterwards

Where a client key doesn't fit, reconnect and look for the result, using something the transaction wrote.

## Call SaveChanges again

A failed `SaveChanges` always runs in a transaction, or a savepoint inside one. On failure nothing is saved, generated keys are cleared and the pending changes stay in the tracker, so you can call it again. If the failure was a lost commit, check first, or the rows go in twice.
