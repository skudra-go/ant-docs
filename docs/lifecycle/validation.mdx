title: Validation
description: Check entities before they are inserted or updated.
---

Validation runs before every insert and update, an `Upsert` included. A failure stops the write. It runs with [hooks](/lifecycle/hooks-and-observers), so bulk writes and `ant.WithoutHooks` skip it.

## Add a rule to a field

`b.Validate` attaches a rule typed to one field. The `validate` package has common rules.

```go
type Signup struct {
	ID    int64
	Name  string
	Email string
	Age   int
}

func (Signup) Configure(b *ant.ModelBuilder[Signup]) {
	// spot-start
	b.Validate(&Signups.Name, validate.All(validate.Required[string](), validate.MaxLength(50)))
	b.Validate(&Signups.Email, validate.Email)
	b.Validate(&Signups.Age, validate.Range(0, 150))
	// spot-end
}

var Signups = ant.Fields[Signup]()
```

| Rule | Checks |
| --- | --- |
| `validate.Required[V]()` | Not the zero value |
| `validate.Email` | A valid address |
| `validate.MinLength(n)`, `validate.MaxLength(n)` | String length |
| `validate.Range(low, high)` | Between two values, both included |
| `validate.OneOf(a, b, c)` | One of these |
| `validate.Matches(pattern)` | Matches a `*regexp.Regexp` |
| `validate.All(rules...)` | All of them |

A rule is a `func(V) error`:

```go
func noSpaces(s string) error {
	if strings.Contains(s, " ") {
		return errors.New("must not contain spaces")
	}

	return nil
}
```

## Fields the database fills {#fields-the-database-fills}

A field with a `default=` tag left at its zero value is left out of an insert, and the database fills it, so its rules don't run there. `Insert` and the inserts of `SaveChanges` skip them. A value you set is still checked.

```go
type Plan struct {
	ID     int64
	Name   string
	// spot-next-line
	Status string `ant:"default='active'"`
}

func (Plan) Configure(b *ant.ModelBuilder[Plan]) {
	b.Validate(&Plans.Status, validate.OneOf("active", "paused"))
}

var Plans = ant.Fields[Plan]()

err := db.Plans.Insert(ctx, &Plan{Name: "Pro"})
// INSERT INTO "plans" ("name") VALUES ($1) RETURNING "id", "status"
// err == nil, and Status is "active"
```

An update writes the zero rather than the default, so updates still check it: saving a tracked `Plan` whose `Status` you set to `""` fails with `ant: Plan.Status: must be one of [active paused]`. So does an `Upsert`, whose update writes the zero too. A [`Validate` method](#check-rules-that-span-fields) sees the entity as you gave it, zero included.

## Check rules that span fields

A rule across several fields goes in a `Validate` method on the model. It runs on insert and update, after the field rules, and only if they all pass.

```go
// spot-start
func (s *Signup) Validate(ctx context.Context) error {
	if s.Age < 18 && s.Email == "" {
		return errors.New("minors need a parent's email")
	}

	return nil
}
// spot-end
```

## Read the error

Field rules don't stop at the first failing field. The write joins one `*ant.ValidationError` per failure, with `errors.Join`. Each names the model and field, and wraps the rule's error, so `errors.Is` works with `validate.ErrRequired` and your own errors.

```go
err := db.Signups.Insert(ctx, &Signup{Email: "not-an-email", Age: 999})
// ant: Signup.Name: is required
// ant: Signup.Email: must be an email address
// ant: Signup.Age: must be from 0 to 150

// spot-start
var invalid *ant.ValidationError

if errors.As(err, &invalid) {
	fmt.Println(invalid.Model, invalid.Field, invalid.Err) // Signup Name is required
}
// spot-end

errors.Is(err, validate.ErrRequired) // true
```

`errors.As` finds the first failure. The error is joined even when only one rule fails, so a type assertion such as `err.(*ant.ValidationError)` never matches: use `errors.As`. To read every failure, walk the error tree. This helper collects them by field, through the join and through any `fmt.Errorf("...: %w", err)` your own code adds:

```go
// FieldErrors returns the message of each failed field rule in err, by field name.
func FieldErrors(err error) map[string]string {
	fields := map[string]string{}

	var walk func(error)
	walk = func(err error) {
		switch e := err.(type) {
		// spot-start
		case *ant.ValidationError:
			fields[e.Field] = e.Err.Error()
		case interface{ Unwrap() []error }:
			for _, inner := range e.Unwrap() {
				walk(inner)
			}
			// spot-end
		case interface{ Unwrap() error }:
			walk(e.Unwrap())
		}
	}

	walk(err)

	return fields
}
```

`Field` is the Go field's name, as in `Name`. `Model` is the model's type name, which tells apart two entities saved together.

## Return validation errors to an API client {#return-validation-errors-to-an-api-client}

Answer a write that fails its rules with a 422 that lists every field, using `FieldErrors` from above:

```go
func createSignup(w http.ResponseWriter, r *http.Request) {
	var signup Signup

	if err := json.NewDecoder(r.Body).Decode(&signup); err != nil {
		http.Error(w, "invalid JSON", http.StatusBadRequest)

		return
	}

	err := db.Signups.Insert(r.Context(), &signup)

	// spot-next-line
	if fields := FieldErrors(err); len(fields) > 0 {
		w.Header().Set("Content-Type", "application/json")
		w.WriteHeader(http.StatusUnprocessableEntity)
		json.NewEncoder(w).Encode(map[string]any{"errors": fields})

		return
	}

	switch {
	case ant.IsUniqueViolation(err):
		http.Error(w, "that email is already registered", http.StatusConflict)
	case err != nil:
		http.Error(w, "internal error", http.StatusInternalServerError)
	default:
		w.WriteHeader(http.StatusCreated)
		json.NewEncoder(w).Encode(signup)
	}
}
```

```http
HTTP/1.1 422 Unprocessable Entity
Content-Type: application/json

{"errors":{"Age":"must be from 0 to 150","Email":"must be an email address","Name":"is required"}}
```

A client that knows the fields by their JSON names needs a map from the Go name, which a framework's validator often has already. The same walk feeds any error format your service uses, such as a list of violations for gRPC's `BadRequest` or an RFC 9457 problem document.

An error from a `Validate` method is not an `*ant.ValidationError`, so `FieldErrors` returns nothing for it, and it lands in the `err != nil` case. Return your own error type from `Validate` and match it with `errors.As` to answer it with a 422 too.

Rules cannot replace a database constraint: a rule can pass while another request inserts the same value, and only the unique constraint catches it.
