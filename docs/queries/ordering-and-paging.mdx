Ordering takes [field pointers](/models/field-probes), so a request can't inject a column name.

## Order by a column

`OrderBy` and `OrderByDesc` start an ordering. `ThenBy` and `ThenByDesc` add to it.

```go
users, err := db.Users.OrderBy(&Users.Age).ThenByDesc(&Users.Name).All(ctx)
// SELECT ... FROM "users" ORDER BY "users"."age", "users"."name" DESC
```

`ThenBy` without an ordering before it returns `ant.ErrThenWithoutOrder`. They take a field of any type, so a nullable, `uuid.UUID` or `decimal.Decimal` column sorts as a plain one does, and the database says if it can't order one. `Latest` and `Oldest` take any field too.

## Order by an expression or place NULLs

`Order` takes terms built from [expressions](/queries/expressions), for case-insensitive sorts and `NULL` placement.

```go
users, err := db.Users.
	Order(
		ant.Col(&Users.Bio).Asc().NullsLast(),
		ant.Lower(&Users.Name).Desc(),
	).
	All(ctx)
// SELECT ... FROM "users" ORDER BY "users"."bio" NULLS LAST, LOWER("users"."name") DESC
```

PostgreSQL has `NULLS FIRST` and `NULLS LAST`. MySQL, MariaDB and SQL Server put NULLs below every value, so ant writes a `CASE` before the value there, and only for the two orders that move them: `Asc().NullsLast()` and `Desc().NullsFirst()`. Under `Distinct` that `CASE` is outside the select list, which SQL Server refuses, so those two return `ant.ErrUnsupported` there. See [databases](/reference/databases#ordering-on-sql-server).

## Sort by a column the request names {#sort-from-a-request}

A request names its sort as text. List the names it may use in a map of `ant.FieldRef`, and order by the entry's `Asc` or `Desc`:

```go
sorts := map[string]ant.FieldRef{
	"name": ant.F(&Users.Name),
	"age":  ant.F(&Users.Age),
}

field, ok := sorts[r.URL.Query().Get("sort")]
if !ok {
	return errors.New("unknown sort")
}

// spot-next-line
users, err := db.Users.Order(field.Desc(), sorts["name"].Asc()).All(ctx)
// SELECT ... FROM "users" ORDER BY "users"."age" DESC, "users"."name"
```

## Newest, oldest, random

```go
newest, err := db.Users.Query().Latest(&Users.CreatedAt).First(ctx)
// SELECT ... FROM "users" ORDER BY "users"."created_at" DESC LIMIT $1

oldest, err := db.Users.Query().Oldest(&Users.CreatedAt).First(ctx)
// SELECT ... FROM "users" ORDER BY "users"."created_at" LIMIT $1

shuffled, err := db.Users.Query().OrderByRandom().All(ctx)
// SELECT ... FROM "users" ORDER BY RANDOM()
```

`ClearOrder` removes an ordering.

```go
plain, err := db.Users.OrderBy(&Users.Name).ClearOrder().All(ctx)
```

## Limit and offset

```go
users, err := db.Users.OrderBy(&Users.Name).Limit(10).Offset(20).All(ctx)
// SELECT ... FROM "users" ORDER BY "users"."name" LIMIT $1 OFFSET $2   -- $1 = 10, $2 = 20
```

Without an ordering, the database picks which rows `Offset` skips. A negative `Limit` or `Offset` is an error at the terminal call on every database, where SQLite would read `LIMIT -1` as no limit.

`Page`, `Chunk` and `ChunkByKey` read inside a `Limit` and `Offset` the query already has, so a shared `Limit(1000)` query chunks those 1000 rows and no more, and `Page` counts its `Total` within them too.

## Numbered pages

`Page` returns the rows plus totals. Pages count from 1. A page past the end has empty `Items` and the right `Total`. A page or size below 1 is an error.

```go
page, err := db.Users.OrderBy(&Users.Name).Page(ctx, 2, 10)
// SELECT COUNT(*) FROM "users"
// SELECT ... FROM "users" ORDER BY "users"."name" LIMIT $1 OFFSET $2   -- $1 = 10, $2 = 10
if err != nil {
	return err
}

fmt.Println(page.Items)     // this page's rows
fmt.Println(page.Total)     // rows in all
fmt.Println(page.Pages())   // pages in all
fmt.Println(page.HasNext()) // is there another?
```

Order the query, or pages may overlap. The count ignores the ordering. Counting and skipping rows gets slow on large tables; use a cursor there.

### Send a page as JSON {#page-json}

`ant.Page` encodes with camelCase keys, as `ant.Base` does, so a handler can write it as it is. `Pages()` and `HasNext()` are methods, so they aren't in the JSON:

```go
page, err := db.Users.OrderBy(&Users.Name).Page(ctx, 1, 20)
if err != nil {
	return err
}

err = json.NewEncoder(w).Encode(page)
// {"items":[{"id":1,"createdAt":"2026-11-01T09:00:00Z","updatedAt":"2026-11-01T09:00:00Z","Name":"Ann",...}],
//  "total":2,"number":1,"size":20}
```

The model's own fields keep Go's names, `Name` and `Age`, unless they have `json` tags. To send other keys, such as `page` and `perPage`, or the page count, copy the page into a response type of your own:

```go
type UserList struct {
	Users   []*User `json:"users"`
	Page    int     `json:"page"`
	PerPage int     `json:"perPage"`
	Pages   int     `json:"pages"`
	Total   int64   `json:"total"`
}

// spot-start
list := UserList{
	Users:   page.Items,
	Page:    page.Number,
	PerPage: page.Size,
	Pages:   page.Pages(),
	Total:   page.Total,
}
// spot-end
```

## Cursors for infinite scroll

`After` pages by position in the ordering. Every page costs the same however deep it goes, and rows added meanwhile don't shift pages. Pass `""` for the first page. Hand `Next` to the client and take it back as the cursor.

```go
query := db.Users.OrderBy(&Users.Name)

page, err := query.After(ctx, "", 20)
// SELECT ... FROM "users" ORDER BY "users"."name", "users"."id" LIMIT $1   -- $1 = 21

next, err := query.After(ctx, page.Next, 20)
// SELECT ... FROM "users"
// WHERE (("users"."name" > $1) OR ("users"."name" = $2 AND "users"."id" > $3))
// ORDER BY "users"."name", "users"."id" LIMIT $4
```

`After` asks for one row more than the page size to detect another page. `Next` is empty on the last page. The key is added to the ordering as a tie-breaker, so no row is lost at a page boundary. With no ordering it pages by key.

The ordering must use plain columns of this table. A query with its own `Limit` or `Offset` is `ant.ErrCursor`, since a cursor has no count of the rows before it, and so is a tampered cursor. `After` reads the key and the ordering columns even when `Column` or `Omit` left them out. `CursorPage` encodes as `{"items":[...],"next":"WyJBbm4iLDFd"}`.

### Page a column that can be NULL {#cursor-nulls}

A pointer or `sql.Null` field can hold `NULL`, and `published_at < $1` never matches a `NULL`, so the pages would end where the `NULL` rows begin. Say where the `NULL`s go with `NullsFirst` or `NullsLast`, and `After` seeks past them with `IS NULL` and `IS NOT NULL`. Here the newest published stories come first, and the drafts after them:

```go
type Story struct {
	ant.Base
	Title       string
	PublishedAt *time.Time
}

var Stories = ant.Fields[Story]()

// spot-next-line
feed := db.Stories.Order(ant.Col(&Stories.PublishedAt).Desc().NullsLast())

page, err := feed.After(ctx, "", 20)
// SELECT ... FROM "stories" ORDER BY "stories"."published_at" DESC NULLS LAST, "stories"."id" LIMIT $1

next, err := feed.After(ctx, page.Next, 20)
// SELECT ... FROM "stories"
// WHERE ((("stories"."published_at" < $1 OR "stories"."published_at" IS NULL))
//   OR ("stories"."published_at" = $2 AND "stories"."id" > $3))
// ORDER BY "stories"."published_at" DESC NULLS LAST, "stories"."id" LIMIT $4
```

Once the cursor reaches the drafts, its value is `NULL`, and the next page reads `WHERE (("stories"."published_at" IS NULL AND "stories"."id" > $1))`. Without `NullsFirst` or `NullsLast`, `After` returns `ant.ErrCursor` before reading a row:

```text
ant: invalid cursor: PublishedAt can be NULL, and each database puts NULLs in its own place: order it with NullsFirst or NullsLast
```

The databases put `NULL`s in different places, PostgreSQL after every value and the other four before, so naming the place gives the same pages on all five. A column that can't hold `NULL`, such as one configured `NotNull`, has none to place, and `After` leaves the `NULLS LAST` out of its SQL. A `Where(ant.IsNotNull(...))` doesn't count as a place.

## Process everything in batches {#chunks}

`Chunk` reads a large result in groups, holding one in memory at a time. `Include` works per group, and returning an error stops it. A size below 1 is an error.

```go
err := db.Users.OrderBy(&Users.Name).Chunk(ctx, 500, func(users []*User) error {
	return send(users)
})
// SELECT ... FROM "users" ORDER BY "users"."name" LIMIT $1 OFFSET $2   -- 500, 0
// SELECT ... FROM "users" ORDER BY "users"."name" LIMIT $1 OFFSET $2   -- 500, 500
// ... until a group comes back short
```

func send(users []*User) error {

On a tracking context, `Chunk` releases the tracker before it calls your function, so the function can query the same context. See [one tracking context, one operation at a time](/queries/reading-rows#one-tracking-context-one-operation-at-a-time).

### Changing rows while you read

`Chunk` pages by offset, so deleting rows in the callback makes it skip others. `ChunkByKey` keeps its place by key, in key order, so the callback can change or delete what it reads.

```go
err := db.Users.Where(ant.Gt(&Users.Age, 100)).ChunkByKey(ctx, 500, func(users []*User) error {
	for _, user := range users {
		if err := db.Users.DeleteByID(ctx, user.ID); err != nil {
			return err
		}
	}

	return nil
})
// SELECT ... FROM "users" WHERE "users"."age" > $1 ORDER BY "users"."id" LIMIT $2
// SELECT ... FROM "users" WHERE "users"."age" > $1 AND "users"."id" > $2 ORDER BY "users"."id" LIMIT $3
```

`ChunkByKey` reads the key even when `Column` or `Omit` left it out. A composite key is paged by the whole key, as `After` pages, and a model without a primary key returns `ant.ErrNoKey`.

## Which one

| You need | Use |
| --- | --- |
| Page numbers in a small table | `Page` |
| An infinite scroll or a public API | `After` |
| To process everything in batches | `Chunk`, or `ChunkByKey` if you change rows |
| To stream without batches | [`Each`](/queries/reading-rows#each) |
